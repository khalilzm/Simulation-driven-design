# 可配置分析计划

`shared/src/analysisPlan.ts` 定义带版本的分析计划与运行时校验；`plan.ts` 执行已选择的能力。当前支持 daylight、sunlight、pedestrian，每个模块实例有独立 moduleId，同一能力允许多个不同工况实例。顺序由 steps 数组确定，空计划返回空结果且不调用引擎。

```ts
const plan = {
  schemaVersion: '1',
  steps: [{ moduleId: 'egress-standard', capability: 'pedestrian', config: pedestrianConfig }],
};
```

计划中的配置采用各能力自己的类型和校验，不把照度、日照时长和疏散时间合并为一个指标。完整计划先校验版本、能力、重复步骤、工况及模型中的目标/人数引用，之后才启动第一个引擎；采光还检查评价高度。未实现的能力直接拒绝。

执行器在启动时复制计划和模型，传给每项引擎独立的副本，防止调用方或某个适配器修改后续步骤的输入。步骤失败或取消时停止后续步骤；各引擎保留自己的任务与结果文件。moduleResults 按实例返回结果，不填充未执行模块的零值或假结果；results 仅提供单实例能力的兼容摘要，多个同能力实例不会覆盖为一个结果。

## 场景和比较策略

- 当前住宅验收流程默认采用室内采光，其预设计划不会附带运行日照或疏散。这是当前工作流选择，不是住宅支持能力的边界；住宅工作区可显式组合其他已实现能力及多个工况。
- 优化的 analysisPlan 模块根据保存的工况选择日照和疏散，simulate 通过同一执行器计算并转换为现有 OptimizationEvaluation。日照完整性检查仍在启动疏散前执行；人数和疏散数值检查也保留。
- 当前优化比较策略的目标是疏散改善且日照不退化，所以它要求两项同工况的分析。只做疏散、只做采光等组合可以独立执行，但套用该比较策略时会在物理计算前拒绝；对应场景需要自己的评价/比较规则。

执行选择与评价策略分开：计算 completed 不表示目标达标，计划执行器不替消防或可达性规则作结论。此阶段没有增加商业/办公空实现，也没有在优化界面增加会改变现有比较规则的能力开关。

## 保存与兼容

新优化任务及工作台分析记录保存 analysisPlan；历史记录未包含计划时由原比较策略构造相同的默认计划。住宅候选目录新增 analysis-plan.json，记录用于该候选采光试算/后续评价的计划；保存计划不代表所有步骤已经执行，仍需结合评价记录判断。

现有引擎任务文件、结果类型、工况 hash 和比较输出保持兼容。场景、规则、计划、模块实例版本和引擎版本已通过 [结果身份](identity.md) 纳入缓存与可比性判断；moduleVersion 在工作区到执行计划的转换中保留。计划选择与执行已经从固定 simulate 调用序列中分离。

回归覆盖单项/空计划不多调用引擎、完整预检、输入副本隔离、失败/取消短路，以及优化摘要兼容和策略不匹配提前拒绝。测试适配器用于验证执行选择，真实 Radiance recipe 继续单独验收。

执行器将每个步骤的 moduleId/moduleVersion 传入 [公共引擎任务运行时](task.md)，三种能力均返回 taskId/inputHash/result/simulationDir。运行中失败仍停止后续步骤；已经执行的任务保留各自目录与终态记录，尚未增加独立的计划级任务队列。
