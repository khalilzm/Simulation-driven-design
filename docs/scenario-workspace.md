# 工作区：底图 + 空间节点 + 多个仿真模块

住宅、商业、办公定义空间业务；采光、日照、疏散等是可组合的分析能力，两者不绑定为一对一关系。现阶段住宅流程以室内采光作为默认验证项，这不是住宅能力白名单。场景定义的 defaultAnalysisIds 只说明当前默认项，显式配置的仿真模块决定实际执行。

## 核心输入

`ScenarioWorkspaceInputs`（shared/src/scenarioWorkspace.ts）包含：

```text
工作区
├── 场景引用：用途、版本
├── 底图/地图引用：资源、版本、输入类型
├── 空间节点图引用：需求资源、版本
└── 仿真模块实例列表
    ├── 模块 ID、版本
    ├── 分析能力
    └── 独立工况与目标
```

底图引用允许 dxf 或 map 类型；当前产品已实现 DXF 输入，地理地图/GIS 的加载和几何转换适配器尚未实现。地图资源本身不能代替分析所需的 SpaceModel。

空间需求与仿真配置是不同输入。一个住宅工作区可以显式选择日照和疏散、不选采光；也可以同时设置采光、日照和多个疏散工况。热、声、消防等后续能力通过全局能力与引擎接入，未实现能力仍明确拒绝，不能显示假结果。

## 多实例计划与结果

分析步骤可带 moduleId；同一能力可出现多次，前提是各实例 ID 不重复。例如 egress-standard 与 egress-alternate 均使用 pedestrian，但可以保存不同人数、种子和时长条件。当前计划数量上限为 128。

`createScenarioAnalysisPlan` 经场景注册入口验证工作区，调用场景的计划构造函数。住宅实现接受工作区显式模块，不自动补入默认采光。`runAnalysisPlan` 根据模块 ID 返回 moduleResults，多个同能力结果不会相互覆盖。results 仅为能力在计划中出现一次时提供的兼容摘要，存在多个工况时不自动选择其中一个。

历史没有 moduleId 的步骤以能力名称作为实例 ID，因此现有单工况计划保持兼容；两个没有显式 ID 的同能力步骤仍会作为重复实例拒绝。

每个实例使用独立配置和模型副本，能力自己的目标检查、引擎和适用性校验仍然有效。工作区选择分析与“哪套规则用于判断/比较”是两件事：现有疏散优化比较策略需要日照保护结果，这不意味着所有住宅分析都需要日照或只允许采光。

## 展示与当前接入范围

现有 dxf/graph/metrics/scheme 四块白板是展示容器，不能作为业务模块数量限制。metrics 可以汇总多个仿真实例；生成方案是输出容器，不是替代底图或需求输入。

本轮已实现工作区输入契约、场景计划构造和多实例执行/结果隔离。现住宅页面仍采用单项采光验证入口，既有生成前置检查也属于该验收流程；前端多模块编辑、各模块结果切换以及将工作区输入完整保存/恢复到页面的接线尚未完成。新增契约不宣称这些界面已经可用。

后续页面应通过仿真模块列表装配配置与报告，按照每个实例的模型/需求/工况版本关联结果；不再以建筑用途决定固定唯一仿真模块。

空间节点的需求语义与图形排版分别计版本。住宅实现将节点坐标和连线显示端点存入独立布局数据，排版版本不作为仿真输入资源版本；同一文件原子保存并保留兼容读取视图。见 [住宅节点图排版版本](residential-graph-layout.md)。
