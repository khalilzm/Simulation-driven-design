---
name: door-width-optimization
description: 在已授权的一个门洞、功能空间或外窗上，理解用户的疏散与日照优化意图，从程序提供的有效候选中选择并组合成多个不同方向的试算方案。
---

用于本项目首轮局部改造。服务器显式加载本文件；不是一个独立 Agent，也不自行启动仿真。

- 六种操作：门洞增宽（resizeOpening + widthM）、门洞位移（moveOpening + position）、隔墙偏移（offsetPartition + wallId + offsetM）、功能交换（swapProgram + spaceA + spaceB）、外窗增宽（resizeWindow + openingId + widthM）、外窗位移（moveWindow + openingId + position）。
- 给出 2～4 个不同方向的候选方案，每个方案是一个「operations」数组（多个操作组合成一个完整方案）。覆盖不同取舍：至少一个日照优先、至少一个疏散优先、可选均衡方案。
- 目标判断（关键）：
  - 若基线 baseline 中存在 targetMetRatio < 1 的目标空间（有日照不足），主目标是改善日照；疏散清空时间作为保护项不得明显退化。
  - 若没有日照目标或全部达标，主目标是缩短模拟清空时间；日照作为保护项不得退化。
- 操作选择规则（务必遵守）：
  - 功能交换（swapProgram）只发生在两个功能房间之间（卧室、客厅、书房等），绝不能与走廊、门厅、玄关、过道等交通空间交换。
  - 功能交换只把低日照空间换到「明显更亮」的房间（后者的 meanHours 至少高 0.5h）。
  - 隔墙偏移（offsetPartition）只在隔墙可能遮挡采光时才用；不确定方向时宁可不用。
  - 每个操作都要能解释它为什么改善目标；拿不准是否有益的操作不要放进候选。
- 性能由程序复算判断，所有操作都是待验证假设，不能编造改善秒数或日照小时。
- 用户提出本轮无法满足的硬要求时返回 needs_input，说明冲突，不把用户意图悄悄替换成默认目标。
- 若用户指定了更严格的范围，只选择同时符合该要求的操作；没有可选项时返回 needs_input。
- 理由简短，说明每个方案的取舍方向。summary 保留用户的主要意图及本轮操作范围。
- 只写指定 proposal.json，不写 model.json、不运行引擎、不改输入文件。无法支持时也必须输出结构化结果。
